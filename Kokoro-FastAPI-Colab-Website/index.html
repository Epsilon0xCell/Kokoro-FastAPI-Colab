Kokoro text-to-speech, served from a Colab notebook

A ready-to-run Google Colab notebook for deploying the Kokoro text-to-speech API with GPU acceleration and public access via an ngrok tunnel.

What this is

I wanted a Kokoro text-to-speech endpoint I could point SillyTavern at without renting a GPU box. This repo is my answer: one notebook, launch_kokoro.ipynb, four cells. The single code cell installs the client pieces (requests, loguru, pyngrok), installs espeak-ng from apt, clones the upstream server, downloads the model into the folder its start script expects, starts the GPU server on port 8880, waits for it, tests it with a real speech request, and then opens the tunnel.

Credit where it belongs: the speech server itself is not my code. The notebook clones remsky/Kokoro-FastAPI at run time and starts its start-gpu.sh. What is mine is the launcher around it: the config block at the top, the readiness checks, the test call that saves test_output.mp3 as proof, the tunnel setup with its fallback, and the loop that keeps the session alive. An earlier version of the README claimed Cloudflare tunnels. The notebook contains no Cloudflare code at all (the campaign counted 42 ngrok mentions and zero Cloudflare), and that claim is corrected in the README and stays corrected here.

The whole launcher stays in one cell on purpose. Colab runs a notebook top to bottom in one shared namespace, so the config, the server thread, and the tunnel live together. Splitting the cell would let the tunnel half run before the server half.

Base addresses

Localhttp://localhost:8880 inside the Colab runtime, where the notebook tests the API before any tunnel exists.
PublicThe ngrok URL the notebook prints at the end of setup. Set NGROK_CUSTOM_DOMAIN to a reserved ngrok domain and that address is used; if the custom domain fails, the notebook falls back to a standard ngrok URL in the same attempt instead of failing the setup.
Use in an appPut the public URL into SillyTavern or another application as an OpenAI-compatible TTS endpoint, as the notebook's final output instructs.

Endpoints

GET /v1/audio/voices

Lists the voices the loaded model offers. This is also the readiness probe: wait_for_api polls this endpoint once a second for up to 180 attempts, and the test function reads its answer carefully instead of trusting one shape, printing the first five voice ids and a count of the rest, or saying plainly when the answer came back in a different format than expected.

GET {public_url}/v1/audio/voices

POST /v1/audio/speech

Turns text into audio. The notebook's own test call, copied from test_api in the code cell, is the honest example of this endpoint, including the voice it uses:

POST {api_url}/v1/audio/speech
Content-Type: application/json

{
  "model": "kokoro",
  "input": "Hello, this is a test of the Kokoro text-to-speech API!",
  "voice": "af_bella",
  "response_format": "mp3"
}

On a 200 answer the notebook saves the returned audio to test_output.mp3. I test with a real speech request, not only the voices list, because an endpoint can list voices while synthesis itself is still broken.

GET /web

The server's web interface, at {public_url}/web as printed by the notebook when the tunnel opens. It belongs to the upstream server the notebook clones; I list it because the notebook prints it as part of the finished setup.

GET /docs

The FastAPI docs page for the cloned server, at {public_url}/docs, also printed by the notebook at setup. If you want the upstream server's own full reference, that page is it, served by the running instance itself.

Start it

  1. Open the notebook in Google Colab: the Colab link for launch_kokoro.ipynb, or use the Open in Colab badge in the repo README.
  2. In Colab, go to Runtime, then Change runtime type, and select T4 GPU.
  3. Set NGROK_AUTH_TOKEN in the configuration block at the top of the code cell to your own ngrok auth token. The placeholder value is rejected by the notebook itself with a clear error. Set NGROK_CUSTOM_DOMAIN too if you reserved a domain (in the ngrok dashboard: Reserved, then Reserve a Domain).
  4. Run the notebook. It sets up the server, waits up to 180 seconds for the API, tests it, and creates the public URL.
  5. Keep the notebook running. The final loop sleeps and prints a status line each minute; that loop is the point, not a hang, because a finished cell lets Colab reclaim the runtime and the tunnel dies with it.

How readiness works

Readiness is judged by two signals, and the notebook trusts neither alone. A reader thread scrapes the server's own log lines for its stage markers (loading the model, creating the pipeline, warmup, startup complete), while wait_for_api polls the voices endpoint. The endpoint can answer before the model finishes loading, and log lines can lag when output is buffered. If the 180 seconds run out but the server process is still alive, the notebook takes one longer look and then asks the person watching whether to continue, because a slow load is not the same thing as a dead one.

Limits, stated plain

Hosted on Colab means session-bound. The notebook's second cell is a browser-console snippet that clicks Colab's connect button every 60 seconds to hold the session; it only helps while that tab stays open, and it is unverified against the current Colab interface. The tunnel function returns None on failure instead of raising, on purpose: by the time it runs, a loaded model on a GPU is already up locally, and a tunnel problem should not throw that away. And the campaign limit, which I keep on this page: no live Colab run was attempted in the improvement passes, because a live run needs a T4 GPU session and a real ngrok token. GPU start-up, model download, and tunnel creation are as coded in the notebook, not as observed.
